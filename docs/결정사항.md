## A. `articles`-`videos` 연결 방식

**결정**: FK가 아니다. `articles.youtube_video_id`는 유튜브 영상 ID를 담는 `text` 컬럼(nullable)이다.

**이유**: 콘텐츠에 붙일 영상이 큐레이션 채널 수집분(`videos` 테이블)에 없을 수 있음. 유튜브 어디서든 영상을 골라 붙일 수 있어야 함.

**비고**: PRD/기획서에서 `video_id`로 표기된 부분은 `videos.youtube_id`와 명칭이 혼동되므로 `youtube_video_id`로 통일함.

## B. `articles.slug` 검증

**결정**: 서버 검증 없이 DB `CHECK` 제약(`^[a-z0-9]+(-[a-z0-9]+)*$`)으로만 강제한다.

**이유**: 1차 범위에는 콘텐츠 등록 API/관리자 GUI가 없고, 콘텐츠는 Supabase 대시보드에서 직접 입력됨. 검증을 수행할 애플리케이션 서버 레이어 자체가 없으므로 DB 제약이 유일한 실질적 방어선임.

---

## C. `comments.target_type` 허용값

**결정**: `'article' | 'video' | 'guestbook'` 3가지. `target_type = 'guestbook'`이면 `target_id`는 반드시 `null`, 그 외에는 반드시 `not null`이어야 한다. CHECK 제약으로 강제함.

**이유**: 마을회관(방명원) 반응은 특정 콘텐츠·영상을 대상으로 하지 않는 반응이므로 대상 자체가 없음.

---

## D. `comments`의 IP 저장 방식

**결정**: 평문 IP 대신 해시(`ip_hash`)로 저장한다. 공개 조회는 `comments` 테이블이 아니라 `ip_hash`를 제외한 `comments_public` 뷰를 통해서만 이루어진다.

**이유**: 레이트 리밋(D-04, IP 기준 1분 3건) 판정에는 해시로 충분하고, 원본 IP를 남기지 않아 개인정보 노출 위험을 줄임. `comments` 테이블에는 anon용 `SELECT` RLS 정책 자체를 두지 않아, 뷰를 우회해 직접 테이블을 조회해도 결과가 비어 있음.

---

## E. `visitors` 스키마

**결정**: `docs/비버마을_기획서_v1.1.md` 6-1의 스키마(단일 행 카운터, `id` 고정값 1)를 그대로 사용한다. 증가는 `increment_visitor_count()` (`SECURITY DEFINER`) RPC 함수로만 허용하고, anon에게 직접 `UPDATE` 권한을 주지 않는다.

## F. 기능 ID 체계

**결정**: 앞으로 기능을 가리킬 때는 **기능명세서(`docs/비버마을_기능명세서_v1.md`) 기준 ID만 사용**한다. PRD의 `F-01`~`F-10`은 화면 번호였음(작성 실수) — 화면을 지칭할 때는 ID 대신 경로로 부른다. (예: "대문", "`/library` 목록", "`/library/[category]/[slug]` 상세")

---

## G. ADMIN 권한과 RLS

**결정**: ADMIN(운영자)은 RLS 정책의 대상이 아니다. Supabase 대시보드는 `service_role`/`postgres` 역할로 접속하며, 이 역할들은 RLS를 우회한다. 따라서 **ADMIN을 대상으로 한 RLS 정책은 만들지 않는다.**

**적용**: `articles`(등록·수정), `videos`(등록)에는 anon/authenticated 대상 쓰기 정책이 없고, 이 작업은 전부 대시보드(RLS 우회)에서 이루어짐. `comments`는 2026-08-21부터 승인 절차 자체가 없어짐 — 아래 H-1 참고.

## H. 콘텐츠 상세 페이지의 반응(comments) 렌더링 방식

**결정**: 콘텐츠 상세(`/library/[category]/[slug]`)는 본문·출처·영상까지만 SSG로 유지하고, 반응 목록은 별도의 Client Component(`CommentList`)가 마운트 후 `comments_public` 뷰를 직접 조회해서 채운다.

**이유**: 본문·출처·영상은 거의 바뀌지 않고 SEO 색인이 필요하지만, 반응은 계속 바뀌고 색인 대상이 아니다. 성격이 다른 두 데이터를 한 렌더링 방식(순수 SSG)으로 묶으면 승인된 반응이 재빌드 전까지 보이지 않는 문제가 생김. 페이지 전체를 ISR로 돌리는 방식(C안)도 검토했으나, 본문까지 불필요하게 재검증 대상이 되므로 채택하지 않음.

**적용 규칙**:
- `CommentList`는 Client Component. 마운트 후 조회(로딩 상태를 화면에 노출).
- 로딩 중: 스켈레톤 UI (스피너 금지, `docs/비버마을_PRD_v1.md` 9장 공통 상태 정의와 동일 원칙). 최종 목록과 높이가 크게 다르지 않도록 최소 높이를 지정해 CLS(레이아웃 밀림)를 방지함.
- 조회 실패: 반응 영역만 에러 문구 표시. 페이지의 나머지(본문·출처·영상)는 정상 렌더링에 영향받지 않음.
- 결과 0건: "첫 반응을 남겨보세요" 안내 (막다른 길 금지 원칙).
- `FAQPage` JSON-LD(F-01)에는 반응 데이터를 포함하지 않는다. 질문·답변(본문)만 구조화 데이터에 들어감 — 반응은 SSG 시점에 존재하지 않을 수 있는 데이터이므로 애초에 포함 대상이 아님.

## I. 검색(B-01/B-03)을 RAG로 오버라이드

**배경**: 기획서(`docs/비버마을_기획서_v1.1.md`)와 기능명세서 B-01은 검색을 `ilike` 부분일치 검색으로 정의하고, 임베딩·LLM 기반 답변은 "2차부터 도입"이라고 명시했다(`20260819000000_init_schema.sql` 헤더 주석에도 동일하게 명시됨). 사용자가 이 2차 계획을 앞당겨 검색 기능만 RAG로 구현하기로 결정했다.

**결정**: 검색(`/search`)은 사람이 미리 써놓은 `articles`가 아니라 **논문 원문(`papers`/`paper_chunks`)을 직접 임베딩 검색·인용하는 RAG 구조**로 구현한다. 도서관(`/library`, A-01~A-04)은 기존 큐레이션 글 구조를 그대로 유지하며, 서로 다른 콘텐츠 소스를 쓰는 별개 기능으로 공존한다.

**이유**: 사용자가 앞으로 논문을 읽고 직접 글을 쓸 계획이 없다고 밝힘. "신뢰할 수 있는 답변"의 근거를 사람이 미리 검증해 쓴 글이 아니라, LLM이 실제 논문 발췌문 밖으로 답하지 못하게 강제하는 시스템 프롬프트에서 가져간다.

**적용 규칙**:
- 논문 수집은 저작권상 원문 재게시가 허용되는 자료(CC-BY, CC-BY-SA, public-domain, PMC Open Access)만 대상으로 한다. `papers.license` CHECK 제약으로 강제함(`20260820000000_add_paper_search.sql`)
- 임베딩: Voyage AI `voyage-3-lite`(512차원). 생성: Claude `claude-haiku-4-5-20251001`
- 논문 삽입은 관리자(로컬 스크립트, `SUPABASE_SERVICE_ROLE_KEY`)만 수행하므로 `articles.published` 같은 승인 플래그를 두지 않음
- 유사도 임계값은 하드코딩하지 않고 환경변수(`SEARCH_SIMILARITY_THRESHOLD`)로 뺀다 — 실제 논문 삽입 후 사람이 눈으로 보정해야 하는 값이라 최초 배포 시점 숫자는 잠정치

**비용 통제 장치**: 검색 1회당 Claude 생성 비용이 발생하므로(Haiku 4.5 기준 1회 약 5원, 무제한 허용 시 하루 100회면 월 예산 초과) 아래 장치를 처음부터 넣는다.
- **답변 캐싱**: `search_cache` 테이블 — 정규화된 질문(`normalized_query`) 단위로 캐싱. 동일 질문 재검색 시 임베딩·생성 API를 다시 부르지 않고 캐시를 반환하며 `hit_count`만 증가시킴. 쓰기는 `upsert_search_cache()`(SECURITY DEFINER) 함수로만 허용 — anon에게 직접 INSERT 권한을 주면 누구나 캐시를 조작해 넣을 수 있어 위험함
- **프롬프트 캐싱**: Claude 호출의 시스템 프롬프트(매번 동일한 "발췌문 밖 답변 금지" 지침)에 Anthropic prompt caching 적용 → 캐시 적중 시 입력 비용 10%
- **컨텍스트 절약**: Claude에는 논문 전체가 아니라 매칭된 청크(500~1000자 발췌문)만 전달 — papers를 청크 단위로 저장·검색하는 구조 자체에 이미 내재됨
- **레이트 리밋**: `search_rate_limits` 테이블 + `check_search_rate_limit()`(SECURITY DEFINER) 함수로 IP 기준 요청 수를 제한. 한도 초과 시 임베딩·생성 호출 자체를 막아 비용을 원천 차단
- 캐시·레이트리밋 쓰기는 모두 `comments`/`visitors`에 이미 쓰인 패턴(SECURITY DEFINER 함수를 anon이 호출)을 따름 — 검색 API 경로(`app/api/search/route.ts`)는 `SUPABASE_SERVICE_ROLE_KEY`를 전혀 쓰지 않는다. 이 키는 논문 삽입 스크립트(`scripts/ingest-paper.ts`) 전용

**후속 수정 (2026-08-21, 코드리뷰로 발견)**: 위 "캐시·레이트리밋 쓰기는 anon이 SECURITY DEFINER 함수를 호출" 방식 중 `upsert_search_cache`·`check_generation_budget` 두 개는 실제로는 보호가 안 되고 있었음. SECURITY DEFINER는 함수 내부에서 테이블 RLS를 우회한다는 뜻일 뿐, "누가 이 함수를 호출할 수 있는가"는 별개(GRANT EXECUTE) 문제라서, anon key만 있으면 앱을 거치지 않고 누구나 `supabase.rpc('upsert_search_cache', ...)`를 직접 불러 캐시에 임의 답변을 심거나, `check_generation_budget`을 반복 호출해 월간 생성 한도를 헛되이 소진시킬 수 있었음.

조치: 두 함수의 anon/authenticated EXECUTE 권한을 회수하고(`20260821000200_restrict_search_write_rpcs_to_service_role.sql`), 검색 API에서만 `SUPABASE_SERVICE_ROLE_KEY`로 호출하도록 바꿈(`lib/supabase/serviceClient.ts`). 위 "검색 API 경로는 SUPABASE_SERVICE_ROLE_KEY를 전혀 쓰지 않는다"는 문장은 더 이상 사실이 아님. `check_search_rate_limit`은 인자를 조작해도 호출자 자신의 한도만 바뀔 뿐이라 위험도가 달라 anon 호출을 그대로 유지함.

**관련 마이그레이션**: `supabase/migrations/20260820000000_add_paper_search.sql`, `supabase/migrations/20260821000200_restrict_search_write_rpcs_to_service_role.sql`

**후속 결정 (2026-08-20, 실사용 중 발견)**: 논문 20편만으로는 "비버 꼬리에 뼈가 있어?" 같은 기초적인 질문에도 답을 못 하는 문제가 실제로 나타남 — 이런 기초 사실은 애초에 학술 논문보다 백과사전·정부기관 팩트시트에 실리는 경우가 많아서, 논문만 계속 늘려도 구조적으로 못 채워질 가능성이 높음.

이에 따라 `papers` 테이블에 넣을 수 있는 출처를 **동료심사 논문으로 제한하지 않고, 라이선스가 확인되는 모든 신뢰할 수 있는 자료로 확장**하기로 결정함:
- 미국 연방정부 기관 자료(USGS, USFWS, NPS 등) — 미국 연방정부 저작물은 기본적으로 퍼블릭 도메인
- 위키백과 등 CC-BY-SA 자료
- 기존 CC-BY/PMC-OA 논문도 계속 포함

스키마·CHECK 제약(`papers.license`)은 변경 없음 — 애초에 "논문"이 아니라 "라이선스가 확인된 출처"를 검증하는 제약이었기 때문. `authors` 컬럼에 기관명(예: "USDA Forest Service", "Wikipedia contributors")을 넣는 식으로 기존 스키마 그대로 수용 가능함. 여전히 라이선스 문구를 페이지에서 직접 확인 후에만 채택하는 원칙은 유지함.

## J. `comments` 관리자 승인(D-05) 폐지 — 등록 즉시 공개로 전환

**결정 (2026-08-21, 사용자 결정)**: `comments.approved` 컬럼과 승인 절차를 완전히 없애고, 등록된 반응을 즉시 공개한다.

**이유**: 애초 기획 의도가 "누구나 와서 댓글 달고 공감할 수 있는" 열린 반응이었는데, 최초 구현 당시 기능명세서 D-05(관리자가 Supabase 대시보드에서 승인해야 공개)가 이 의도와 어긋나게 적혀 있었음. 코드리뷰 중 이 불일치가 드러나 사용자가 원래 의도대로 바로잡기로 결정함.

**도배 방지 (승인 절차를 대신함)**:
- 기존: IP 기준 1분 3건 레이트 리밋(D-04, `check_comment_rate_limit`)
- 추가: 같은 IP·같은 대상·같은 내용을 10분 안에 다시 올리면 거부 (`check_comment_duplicate`, `409 DUPLICATE_CONTENT`) — 함수 자체는 읽기만 하고 호출자 자신에게만 영향을 주므로 anon 호출 허용
- 추가: 사이트 전체 하루 500건 총량 제한 (`check_comment_daily_limit`, `503 DAILY_LIMIT_REACHED`) — 공유 카운터를 증가시키는 함수라 I 후속 수정에서 겪은 실수(anon/PUBLIC EXECUTE 권한 누락 확인)를 반복하지 않도록 처음부터 anon/authenticated/PUBLIC 모두에게 권한을 주지 않고, 검색 API의 `check_generation_budget`과 같은 패턴으로 `app/api/comments/route.ts`에서 `SUPABASE_SERVICE_ROLE_KEY`로만 호출함
- 추가: 금칙어(욕설·스팸 키워드) 필터 — `lib/comments/validateComment.ts`, 클라이언트·서버 공용

**적용 범위 밖**: 관리자 승인 화면은 만들지 않음(원래부터 1차 범위 밖, PRD 1-2 참고). 사후 삭제가 필요하면 Supabase 대시보드에서 `comments` 테이블 행을 직접 지운다.

**관련 마이그레이션**: `supabase/migrations/20260821000400_open_comments_add_spam_guards.sql`

## 검증 계획

RLS 정책 적용 후, 익명 클라이언트(anon key)로 직접 아래를 확인한다.

- [ ] `published = false`인 article이 조회되지 않는가
- [ ] `comments` 테이블을 anon으로 직접 SELECT 시 결과가 비어 있는가 (ip_hash 미노출 확인, `comments_public` 뷰로만 조회 가능)
- [ ] anon이 `visitors`를 직접 UPDATE 시도 시 거부되는가
- [ ] `increment_visitor_count()` 호출 시 카운트가 정상적으로 1 증가하는가
- [ ] anon이 `papers`/`paper_chunks`/`search_cache`/`search_rate_limits`에 직접 INSERT 시도 시 전부 거부되는가
- [ ] `upsert_search_cache()`를 같은 질문으로 두 번 호출하면 행이 1개로 유지되고 `hit_count`만 증가하는가
- [ ] `check_search_rate_limit()`을 한도 이상 반복 호출하면 `false`를 반환하는가
